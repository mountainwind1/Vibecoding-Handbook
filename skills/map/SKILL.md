# map · 项目地图（试验中）

> 解决的问题：进度块（`prog`）回答"做到第几个任务"，回答不了"在业务流程的哪一步、问题出在哪块、精力花在哪"——任务一个个做完，项目整体仍是黑洞；过度设计也藏在里面看不见。
> **试验状态**：在两个真实项目的数据上只读跑过；在一个真实项目里完整用满一个里程碑之前，不进手册默认路径。
> 安装：整个目录复制到项目的 `.claude/skills/map/`（Codex：`.agents/skills/map/`）。只用 Python 标准库。可选：装了 [archify](https://github.com/tt-a1i/archify) skill（需要 Node ≥ 18）就多出一张交互架构图；没装照常出自带页面。

## 流程

1. **第一次用：写模块地图**（一次性）。在项目 `ENGINEERING.md` 加「模块地图」一节（格式见模板 `templates/ENGINEERING.md`）：业务线照 PRD 的用户旅程 / 架构蓝图排，路径表把文件归到「模块 × 层」。由 agent 起草、**用户确认一次**再提交。没有这一节也能跑（按目录分组），但画不出业务流程。
2. **生成**，从仓库根：

   ```
   python3 <本 skill 目录>/map.py              # 产物在 ~/.cache/vibe-map/<项目名>/index.html
   python3 <本 skill 目录>/map.py --publish    # 生成后执行地图里的「发布：」命令（云端）
   ```

   把产物路径（或发布后的网址）给用户，**不要在对话里复述页面内容**——页面就是给用户自己看的。
3. **任务收尾**：`kof` 第四步在进度块之前跑一次 `map.py --quiet`（配了发布命令就加 `--publish`），成功时没有任何输出。
4. **云端**：托管由项目自己选，在「模块地图」里写一行 `发布：<命令>`（`{dir}` = 产物目录）。命令是普通 shell，任何 agent 或 CI 都能跑；页面里有安全欠账等敏感内容，**只能发到有访问控制的地方**。

## 页面怎么读

| 你想知道 | 看哪里 |
|---|---|
| 在业务流程的哪一步 | 顶部「当前阶段 / 下一步 / 等你拍板」；线路图上「你在这里」= 本里程碑改动最多的模块（里程碑刚开还没提交时 = 下一个任务提到的模块） |
| 每个模块的页面 / 接口 / 数据 | 「模块」卡片按层列：文件数、本里程碑改了多少行、挂着哪些问题；archify 图上点节点看每层的代表文件，可跳到源码 |
| 问题出在哪 | PLAN 里未勾的 SEC- / EXT- 等条目，和进行中里程碑的「待拍板 / 偏差」，钉到模块（和层）上；「问题」页签有原文和定位依据 |
| 精力花在哪 | 「投入分布」：模块 × 里程碑的改动行数热力图——某个模块的投入远超它在业务里的分量，就是过度设计的嫌疑 |

## 读法（与 prog 同口径，自检里交叉核对）

- 里程碑 = `## M…` 二级标题，含「已收口」或 ✅ 为已收口；`### M2a` 这类子段不算里程碑。
- 进度 = 里程碑下的**顶格**复选框与表格行（`| M3-T4 | … | ✅ |`），含 EXT- / SEC- 条目；缩进子项不算。
- 问题定位是**启发式**，按可靠程度：带目录的文件提及（`api/routes.py`）> 裸文件名（同名文件分属多个模块就放弃）> 关键词（标题 → 所在小节标题 → 正文，取最先提到的）> `.md` 提及。定不了的列进「未定位」——给地图补路径或关键词，别手工改结果。
- 投入 = 改动行数（增 + 删，不含合并提交），只算代码与文档（数据文件、锁文件不算），按提交说明里的里程碑编号归列；只用来比相对大小，不是工作量。

## archify 的约束（实测踩过）

- 每个节点源码证据最多 3 条：按页面 / 接口 / 数据优先。源码链接钉在最后一个已推送的提交上（私有仓库登录后能打开）；没推送过就只显示路径、不出链接。
- 副标题要短：太长会被缩字号，最要紧的「▶ 你在这里」曾因此成了全图最小的字。节点下方的 tag 是 7px 注记，只放次要信息。
- 边框只表达真实的归属 / 信任边界，不拿来当「你在这里」标记——当前位置用章节表达：打开 `archify.html#view=here` 直接定位。
- 出不了图（校验没过）不挡自带页面；archify 的诊断原样打到 stderr。

## 常见借口 → 反驳

| 借口 | 反驳 |
|---|---|
| "我直接给用户讲一下项目全貌就行" | 讲的是会话记忆里的全貌。地图由脚本从 PLAN 和 git 现算，用户能对账；模型转述正是黑洞的来源。 |
| "这个问题定位得不准，我在页面里手工改一下" | 改地图（补路径 / 关键词）或改 PLAN 的写法，重新生成。手改产物下次刷新就没了，还让两份东西各说各话。 |
| "投入热力图显示某模块投入很大，说明它重要" | 投入大 ≠ 重要。它是给用户判断"值不值"的证据，不是结论；把数字摆出来，判断留给用户。 |
| "发布到公开地址方便看" | 页面里有安全欠账原文。只发有访问控制的地方。 |

## 验证

- `python3 map.py --selftest` 输出 `selftest ok`：临时仓库夹具覆盖 PLAN 读法（子段、表格行、缩进子项、EXT- 版本号）并**与 `prog.sh` 交叉核对同一份 PLAN**、问题定位的四级规则与"同名文件不瞎定"、数据文件不算投入、当前位置、archify 的硬上限（源码证据 ≤ 3、章节 ≤ 5、标题 ≤ 48、说明 ≤ 140、网格不重格）、问题原文里的 `</script>` 不炸页面、发布命令的 `{dir}` 替换、没有地图时按目录分组。改守卫逻辑时先确认原版绿，再逐条拿掉守卫看对应断言变红（崩溃不算红）。
